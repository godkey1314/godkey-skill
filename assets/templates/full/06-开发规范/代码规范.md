# 代码规范

> 通用跨语言工程规范。当项目存在自己的规范文档时以项目规范为准；当项目无定制规范时，本文档作为默认基准。
> 原则分层：**第一至十一节为通用硬纪律**；**第十二节为无项目既有范式时的默认风格建议**（项目已有明确范式时以项目范式优先）。

---

## 一、范式优先

在项目中写任何代码前，必须先找到项目中已有的类似实现作为参考。文件组织、命名、方法签名、错误处理与工具选型以**项目现有范式**为准，不以个人偏好或训练数据习惯为准。

1. 查找与当前任务功能相似的已有模块；
2. 阅读其文件结构、类/函数命名、参数与错误返回方式；
3. 新代码保持风格一致；若无参考范式，以简单直接为先。

---

## 二、分层纪律

每一行代码必须有明确架构层级归属。依赖只能单向向下流动，禁止反向或跨层跳跃。

| 层 | 职责 | 严禁越界 |
|---|---|---|
| **接入层** | 接收请求/事件、参数校验、调用业务层、返回响应 | 写复杂业务判断、直接操作持久化设施 |
| **业务层** | 业务逻辑、流程编排、事务边界、跨模块协作 | 直接拼接底层查询语句或操控连接细节 |
| **数据/基础层** | 数据持久化、外部存储/消息队列访问 | 夹带业务条件判断、借用不相关模块的资源 |
| **独立能力层**（可选） | 纯计算/统计、外部 API 适配、AI 推理 | 硬编码上层业务决策 |

---

## 三、模块边界与反过度工程

- **何时新建模块**：有独立业务领域、独立数据模型，或被多个模块复用。
- **何时扩展现有模块**：处理同一业务对象、共享数据模型、属于现有功能延伸。
- **反过度工程**：
  - 不做用户未要求的功能，不“顺手”重构无关模块；
  - 不为单一场景或“将来可能需要”创建无业务价值的抽象层与中间层；
  - 三个相似片段 > 一次过早抽象；直接调用 > 无意义多层委托。

---

## 四、代码清洁度（删除高于保留）

- 废弃字段、方法、导入、历史兼容桥必须直接删除；
- 禁止留墓碑注释（“已移除”“临时方案”“以防万一”）、大段注释代码与无意义兼容兜底；
- 注释只解释**为什么**（业务边界、非显然决策、框架陷阱），不解释显而易见的“做什么”；
- 禁止硬编码凭证（API Key、密码、私钥），禁止随意用 `print` / `console.log` 替代正式日志。

---

## 五、依赖方向与资源归属

- 依赖单向流动，避免循环依赖；
- **不借道访问**：不通过不相关模块间接获取底层资源（数据库连接、会话、客户端句柄），每个模块的资源由自身依赖显式注入。

---

## 六、数据与 I/O 性能铁律

| 禁止 | 替代做法 |
|---|---|
| 加载完整对象列表只为取数量 | 使用计数查询（`COUNT`） |
| 循环内逐条查询（N+1） | 合并为批量查询或单次联查 |
| 同源多指标拆成多次查询 | 合并为单次聚合查询 |
| 无界扫描（无分页/无时间范围） | 明确分页、时间窗或上限 |
| 无界并发（一次性并发启动 N 个协程/线程） | 使用并发上限（如信号量/工作池） |
| 多协程/多线程共享非线程安全会话或连接 | 各自独立获取会话或顺序执行 |

热路径（首页、Dashboard、高频统计）优先读预计算快照或缓存，避免每次请求全量实时计算。

---

## 七、代码重复与抽象时机

横向对比同类文件（同目录、同基类、同接口实现）：

| 重复次数 | 处理策略 |
|---|---|
| 1–2 次 | 保留，不过早抽象 |
| 3–5 次 | 抽取模块内公共函数 |
| 5 次以上 | 抽取基类 / Helper / 独立工具模块 |

---

## 八、值语义陷阱

`0`、空字符串 `""`、空列表 `[]`、`False` 与“值不存在（`None` / `null`）”语义完全不同。禁止用 falsy 判断代替空值判断：

```python
# 错误：rate 为 0 时会被误判为不存在
value = result.get("rate")
rate = to_number(value) if value else None

# 正确：显式区分 None 与 0
rate = to_number(value) if value is not None else None
```

| 语言 | 正确判空方式 |
|---|---|
| Python | `x is not None`（不用 `if x`） |
| JavaScript / TS | `x != null` 或 `x !== undefined && x !== null`（不用 `!x`） |
| Go | 显式区分指针 `nil` 与零值 |
| Java / Kotlin | `Optional` 或显式 `!= null` |
| Rust | `Option<T>` 模式匹配 |
| C# | `x is not null` / `Nullable<T>.HasValue` |

---

## 九、通用组件职责边界

通用组件（任务执行器、框架中间件、公共工具）**不得感知特定业务语义**。通用组件只定义通用协议与数据结构，特定业务分支留在业务模块处理。

---

## 十、测试纪律

- 纯函数单测只是起点，**不得通过 mock 核心依赖掩盖真实链路问题**（详见 GodKey Skill 测试流程规范）；
- 新增数据层方法、核心业务编排、新接口、阈值边界逻辑及 Bug 修复必须有对应自动化验证；
- 禁止注释或 `skip` 失败用例而不查根因；测试数据必须与生产隔离并清理。

---

## 十一、前端通用规范（如项目涉及前端）

- **派生状态稳定**：使用 `computed` / `useMemo` / `$derived`，禁止在渲染路径重建带局部状态的对象；
- **异步竞态保护**：并发/连续触发的异步请求使用递增 token 或 `AbortController` 丢弃过期响应；
- **请求防重**：加载态阻止重复提交/拉取；
- **公共格式化复用**：状态文案、日期、金额、标签颜色抽为公共工具，不跨页面复制粘贴。

---

## 十二、无项目范式时的默认风格建议

> 仅在项目尚无既有风格约定时生效；如项目已有不同惯例（如 Go/Pydantic 同文件多模型、Tailwind/CSS Modules），一律服从**第一节“范式优先”**。

- **业务常量与魔法值**：跨多处使用的状态码、类型标识、业务枚举优先定义为具名枚举或常量，避免裸数字/裸字符串散落。
- **模型组织**：数据持久化实体与对外接口 DTO/视图对象尽量分离，避免直接暴露底层表模型。
- **样式**：有 UI 组件库时优先使用内置组件与主题变量，避免无序散落内联样式。
- **基础格式**：缩进统一不混用 Tab/空格；导入按标准库 → 第三方库 → 本地模块分组；遵循对应语言的命名惯例（如 Python `snake_case`、Java/TS `camelCase`）。
