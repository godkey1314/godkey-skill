# 文档与变更体系

适用场景：项目冷启动初始化、四种运行模式切换、功能包 4 态流转、`ops/` 资产管理、静态文档同步与门禁脚本/Hook 接入。

> **何时加载本文档**：① 前置审计需要初始化新项目文档体系；② 功能开发过程中涉及状态流转（待确认/进行中/搁置）、`ops/` 资产放置或 Hotfix 登记；③ 关卡 5 执行静态文档同步与 `archive` 门禁。

---

## 一、四种运行模式与选择原则

| 模式 | 适用项目 | 文档根目录 | 静态层 | 动态层 |
|---|---|---|---|---|
| **`full`** | 中大型项目、多模块服务、需独立运维与分模块设计 | `doc/` 或 `{project}_doc/` | `01~08` 目录 | `09-迭代变更/` |
| **`lite`** | 小型单体项目、独立工具、希望长期维护但不想太重 | `doc/`（兼容已有 `docs/`） | `01~03` 三个核心文件 | `04-迭代变更/` |
| **`external`** | 外部开源仓库、已有规范文档的历史老项目 | 沿用原仓库结构 | 原项目 `README`/`docs` | 不强建目录 |
| **`demo`** | 一次性 Demo、临时实验验证脚本 | 无 | 豁免 | 豁免 |

### 1. 冷启动初始化流程（`uninitialized` 模式）
1. 先向用户说明当前为新项目，根据体量推荐 **`full`** 或 **`lite`**，**由用户拍板选择**（若是多模块项目同步确认目录名为 `{project_name}_doc/`）。
2. 执行初始化脚本生成骨架与 `.godkey.json`：
   ```bash
   python <skill路径>/scripts/godkey_gate.py init --profile full|lite --doc-root doc --project-root <项目根>
   ```
3. **用户主导填充，够了就停**：AI 逐项向用户提问核心信息（项目定位、技术栈与分层、规范偏好），用户回答、AI 落盘；用户说“先这样/够了”即停，不替用户做产品决策，不死磕填满每个占位文件。

### 2. 外部已有项目策略（`external` 模式）
- 严禁未经用户要求强行往外部仓库塞入 `01~09` 中文目录；
- 通读原仓库 `README.md`、`AGENTS.md`/`CLAUDE.md`、`docs/` 建立基准；
- 完整保留所有防幻觉工程纪律（查框架版本源码、读全上下游、定层清废、模式扩散审查、真实链路测试），改完后同步更新原仓库受影响的既有文档。

### 3. 从 `lite` 平滑升级到 `full`
当小型项目长出多模块或多张数据表时：将 `01~03` 三个单文件拆分为 `01~08` 目录，将 `04-迭代变更/` 重命名为 `09-迭代变更/`，**并将 `.godkey.json` 整体替换为 `assets/templates/full/.godkey.json`（同步更新 `profile`、`changesDir` 与 `staticSyncRules`）**，历史归档包无缝保留。

## 二、动静分离原则（核心架构）

### 1. 静态真相层 = 项目当前最新快照
- 只描述**系统此刻真实运行的状态**，直接覆写更新到最新设计，**禁止**“不删旧内容只靠末尾追加”制造过时僵尸文档。
- **数据库只存快照**：`05-数据库/表结构快照.md` 与 `05-数据库/init_tables.sql`（`lite` 为 `02-架构与设计.md`）永远维护当前最新完整表结构定义，不堆放历史增量迁移文件。

### 2. 动态迭代层 = 按功能驱动的一体化工作包
一个真实需求往往跨多次会话、包含代码改动、迁移 SQL、数据脚本、测试与审查。全部归拢到**同一个功能包目录**（`YYYY-MM-DD_功能名/`）：

```text
2026-11-21_用户导出Excel/
├── 01-方案.md          # 背景、蓝图对齐、代码摸底、分层方案、影响分析与测试要点
├── 02-进展.md          # 跨会话进展、变更前快照、关键决策、静态同步记录与基线 commit
├── 03-测试.md          # 测试计划 + 实测报告
├── 04-审查.md          # 自检循环 + 代码审查报告
└── ops/                # 本次迭代专属动态执行资产
    ├── 01_alter_xxx.sql    # 本次迭代迁移 SQL / 数据订正 SQL
    ├── backfill_xxx.py     # 一次性数据清洗或回填脚本
    └── deploy-notes.md     # 本次上线顺序、新增环境变量与回滚步骤
```

- **跨会话接力唯一入口**：每次新会话接力，直接读 `02-进行中/<功能包>/01-方案.md` 与 `02-进展.md` 即可恢复完整脉络。
- **归档后 `ops/` 的去向**：功能上线归档时，将最终表结构同步到静态数据库快照、新增永久环境变量同步到静态环境配置，过程迁移 SQL 与一次性脚本随功能包整包归档到 `99-已归档/<功能包>/ops/` 作为可追溯历史留痕。
- **支持本地保留（`.gitignore` 忽略动态目录）**：若项目约定只将静态真相层纳入 Git、本地保留 `09-迭代变更/`（或 `04-迭代变更/`），可将该目录加入 `.gitignore`；`godkey_gate.py` 会自动区分“已被 `.gitignore` 忽略且未跟踪”的动态目录，在 `audit`、`commit`、`hotfix`、`archive` 门禁中回退本地磁盘核验活跃进展、Hotfix 台账、产物四件套与包内豁免（使用包内豁免时须显式传 `--package <功能包>`）。

## 三、四态文件夹状态机

文件夹本身就是状态，**禁止在文档正文手写“状态：进行中/已完成”**：

```text
01-待确认/  ──确认方案──▶  02-进行中/  ──同步静态文档 + archive 门禁通过──▶  99-已归档/
                              │  ▲
                 实验暂停/切任务 │  │ 恢复开发
                              ▼  │
                           03-已搁置/
```

| 状态目录 | 含义 | 流转命令 |
|---|---|---|
| `01-待确认/` | 方案已出，等待用户确认拍板 | `godkey_gate.py new <名> --state draft` |
| `02-进行中/` | 当前活跃开发中的功能包 | `godkey_gate.py new <名>` 或 `move <名> active` |
| `03-已搁置/` | 中途暂停的实验或暂缓需求（移出活跃视线并保留现场与原因） | `godkey_gate.py move <名> paused --reason "..."` |
| `99-已归档/` | 已完成、已验收、**静态文档同步门禁已通过**的历史包 | **仅允许** `godkey_gate.py archive <名>` |

- 独立代码审查（无关联开发功能包时）使用 `godkey_gate.py new 审查_<主题> --type review --state active --project-root <项目根>`，仅生成 `04-审查.md` 且归档门禁独立校验该报告。

> 严禁跳过 `archive` 脚本直接手工 `mv` 目录进 `99-已归档/`；在 Git 仓库中严禁使用 `--skip-git`（脚本会直接拒绝）。

## 四、Hotfix 小修台账

针对 Pass 1 判定为单文件、局部根因明确、不改变蓝图与架构的小 Bug 修复，不新建独立功能包目录，直接执行登记与专用门禁：

```bash
python <skill路径>/scripts/godkey_gate.py hotfix \
  --title "修复导出空指针" \
  --symptom "空列表调用 export 抛出 AttributeError" \
  --root-cause "未显式判空 None" \
  --files "src/export.py" \
  --verify "pytest tests/test_export.py 全部通过（含新增回归用例）" \
  --project-root <项目根>

python <skill路径>/scripts/godkey_gate.py check-sync --mode hotfix --project-root <项目根>
```

> `--mode hotfix` 会自动核验：① `hotfix记录.md` 已更新；② 改动业务代码不超过 1 个文件；③ 未触及数据库/运维/架构级变更。超限即拦截并要求走标准功能包。

## 五、确定性门禁与全场景同步映射

### 静态同步触发规则（由 `godkey_gate.py check-sync` 机械检查）

| 变动信号（Git Diff + `ops/`） | `full` 必更静态目标 | `lite` 必更静态目标 | 对应规则键 |
|---|---|---|---|
| 业务源码文件变更（不含纯测试文件） | `04-功能设计/` | `02-架构与设计.md` | `featureDocs` |
| 表结构/ORM/Schema 路径变更，或功能包 `ops/` 存在 `.sql` | `05-数据库/` | `02-架构与设计.md` | `dbDocs` |
| 依赖声明变更，或新增源码顶层模块目录 | `03-系统架构/` | `02-架构与设计.md` | `archDocs` |
| Docker/部署/环境变量模板变更，或 `ops/` 含脚本/已填写 `deploy-notes.md` | `07-部署运维/` | `01-项目说明.md` | `opsDocs` |

### 豁免机制（可审计、防敷衍、防历史毒丸）
若某类改动确实不改变对应静态蓝图（如纯内部函数重命名、不改变外部行为的性能微调），必须在**当前功能包 `02-进展.md`（独立整行）**写入具名原因（至少 8 字且含具体技术/业务依据，脚本会自动拦截“无需更新/本次改动不需要更新文档”等空洞套话；无 `--package` 校验时只认本次 diff 新增的豁免行，历史记录不会形成永久豁免）：

```markdown
<!-- doc-sync-waiver: featureDocs | 纯内部循环重构为批量查询，不改变接口契约与业务规则 -->
```

脚本会在输出中醒目打印所有 `WAIVED` 项供人工审查。同样，如纯文档改动无需测试或审查，可在 `03-测试.md` / `04-审查.md` 中使用：

```markdown
<!-- artifact-waiver: test | 纯文档与配置说明调整，无可执行代码变更 -->
```

### 跨 Harness Hook 兜底
- 在目标项目安装 Git `pre-commit` hook（适用所有 Harness 与人工提交）：
  ```bash
  python <skill路径>/scripts/godkey_gate.py install-hook --project-root <项目根>
  ```
- 各 Harness 专属原生 Hook 示例见 [hooks/README.md](../hooks/README.md)。
