# 代码审查

适用场景：独立代码审查、PR Review、工作区变更审查，以及 [开发流程](开发流程.md) Pass 4 自检。

> **何时加载本文档**：① 独立审查任务；② 开发流程 Pass 4 自检复用 Pass 2 的 5 个维度与 Pass 3 模式扩散。具体检查维度与报告格式只在本文件定义。

---

## 审查纪律

1. **先读基准规范**：打开项目开发规范与系统架构文档，提取可逐条核对的条款（无项目定制规范时以内置 `代码规范.md` 为基准）。
2. **先定范围**：列出本次审查覆盖的全部文件、模块与基线提交。
3. **结论附证据**：禁止笼统写“整体不错/通过”；每个问题必须给出文件路径、行号、违反条款与修复方案。
4. **多轮递进**：找到一个问题模式，必须全范围扩散追查同类隐患。

---

## 审查流程（5 Pass，不可跳轮）

### Pass 1：全景扫描

**目的**：建立全局视图，只标记可疑点、不提前深陷单点。

1. 列出完整文件清单，标注每个文件的架构层级归属；
2. 画出关键调用链与共享资源依赖（数据库连接、会话、缓存、外部客户端）；
3. 标记所有疑似违反规范、破坏分层或偏离既有范式的位置。

**输出**：文件清单 + 分层标注 + 关键依赖关系 + 可疑点列表。

### Pass 2：五维度深追

**目的**：对上轮可疑点及以下 5 个维度逐项追到底（可并发检查）：

1. **维度 1 — 架构合规**
   - 分层越界：每个文件是否只做本层职责？是否存在数据上移、业务下移、跨层跳跃？
   - 依赖借道：是否通过无关模块获取底层资源？
   - 通用组件污染：公共工具/中间件是否混入特定业务判断？
2. **维度 2 — 代码质量**
   - 横向对比同类文件（同目录、同基类、同接口）：是否存在 3 处以上重复模式？
   - 清洁度与语义：是否存在废弃代码、兼容垃圾、墓碑注释、裸魔法值、值语义陷阱（`0`/`""`/`[]` 被当成空值）？
   - 范式一致性与类型/导入完整性。
3. **维度 3 — 性能与数据**
   - 查询方式：N+1 查询？全量拉取只为计数？无界扫描？同源多指标拆分查询？
   - 并发与生命周期：共享资源是否线程/协程安全？并发任务是否有上限控制？是否符合框架真实版本约束？
   - 热路径：高频接口是否走快照/缓存而非反复全量重算？
4. **维度 4 — 测试覆盖**
   - 改动涉及的数据层、业务编排、接口与边界条件是否有自动化测试？
   - 是否验证了真实链路（或受限环境下已显式注明降级与补测项）？
5. **维度 5 — 前端专项**（如涉及前端）
   - 派生状态是否使用计算属性/缓存，避免渲染重建丢状态？
   - 异步请求是否有竞态保护与加载防重？
   - 公共格式化逻辑是否复用？

**输出**：按维度列出具体检查结果（每项附文件、行号与依据条款）。

### Pass 3：模式扩散（核心深度差异）

**目的**：把 Pass 2 在单点发现的问题模式，反向扫描所有同类文件。

> 必问一句：**“这个错误模式，在其他地方还有吗？”**

常见扩散示例：
- 发现一处 N+1 查询 → 排查全部列表/统计接口的循环查询；
- 发现一处并发共享非安全会话 → 检查所有异步/多线程入口的会话创建方式；
- 发现一处 `if rate:` 把 `0` 误判为空 → 全局搜索同类数值/可选字段的 falsy 判断；
- 发现一处遗留迁移 SQL 散落源码目录 → 排查仓库其余未归位临时脚本。

**输出**：扩散排查范围 + 新增问题清单（无新增也要写明排查了哪些同类文件）。

### Pass 4：定级与完整报告

1. 逐文件、逐维度核对无遗漏；
2. 既列问题，也列出经确认**符合规范的部分**；
3. 按 `P0（阻塞）/ P1（高优）/ P2（中优）/ P3（建议）` 分级，并给出分批修复顺序与可逐条验收的 Checklist。

报告章节格式：

```markdown
## 一、审查范围与基准
## 二、完成度与整体结论
## 三、问题清单（P0 / P1 / P2 / P3）
   每条包含：位置（文件:行号） / 问题类型 / 违反条款 / 修复建议（含前后对比）
## 四、模式扩散排查结果
## 五、符合规范的部分
## 六、修复顺序与验收标准
```

### Pass 5：审查报告落盘（口头结论不算数）

按项目模式决定报告落盘位置：
- **关联现有活跃功能包（`full` / `lite`）**：写入该功能包的 **`04-审查.md`**（若是多轮审查，追加轮次标题保留闭环轨迹）；
- **独立审查任务（`full` / `lite`，无现成功能包）**：用 `python <skill路径>/scripts/godkey_gate.py new 审查_<模块或PR名> --type review --state active --project-root <项目根>` 建独立审查包，将报告落盘到 **`04-审查.md`**；审查完毕后直接执行 `godkey_gate.py archive 审查_<模块或PR名> --project-root <项目根>` 归档（独立审查包只校验 `04-审查.md` 实质内容，不与被审工作区代码 diff 冲突；若后续立项修复再按开发流程建功能包）；
- **`external` 模式**：在回复中输出完整报告，并按用户要求落盘到指定路径。

> 禁止在只看纯函数测试通过的情况下放行真实链路隐患；禁止交付只有问题列表而无验收标准的审查报告。
