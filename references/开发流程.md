# 开发流程

适用场景：新功能开发、Bug 修复、代码重构、模块添加、架构调整。

> **与 SKILL.md 的分工**：`SKILL.md` 定义关卡判定标准与阻塞铁律；本文档定义 6 个 Pass 的具体执行步骤、输出格式与分层决策表。收到开发任务，先通读本文档全文再开工。

---

## 全局锁：按 Pass 0 → Pass 5 顺序执行，不得跳过关键门禁。

---

## Pass 0：蓝图与规范对齐（关卡 0 — 只读文档与依赖）

**目标**：防止一上来扎进局部代码打补丁；先建立全局业务视角、架构边界与真实框架约束。

### 1. 读静态真相文档
- **`full` 模式**：通读 `06-开发规范/`、`03-系统架构/`，查阅与本次任务相关的 `04-功能设计/` 与 `05-数据库/表结构快照.md`。
- **`lite` 模式**：通读 `01-项目说明.md`、`02-架构与设计.md`、`03-开发规范.md`。
- **`external` 模式**：通读原仓库已有 `README.md`、`AGENTS.md`/`CLAUDE.md`、`docs/` 等既有文档。
- 若项目未定制编码规范，以本 Skill 内置 `assets/templates/full/06-开发规范/代码规范.md` 作为基准。

### 2. 查活跃变更上下文
- 若 `godkey_gate.py audit` 显示 `02-进行中/` 存在与本次任务相关的功能包，**先读该包的 `01-方案.md` 与 `02-进展.md`**，在原功能包上继续推进，严禁另起炉灶重复建包。

### 3. 识别技术栈与真实框架约束（防弱模型靠猜）
1. 读取项目依赖声明文件（`pyproject.toml`、`package.json`、`go.mod`、`pom.xml` 等），列出关键框架名称与精确版本。
2. 核实框架关键约束（并发安全、会话/连接生命周期、事务传播、序列化行为）：
   - 源码可访问 → 直接打开源码核实；
   - 否则查阅对应版本的官方文档。
3. **严禁凭训练数据记忆猜测框架行为**；无法核实时立即阻塞询问用户。

**输出**：可逐条对照的**规范约束清单 + 框架约束清单**（禁止空喊“注意分层”）。

---

## Pass 1：代码边界摸底（关卡 1 — 只读源码）

**目标**：带着 Pass 0 的蓝图去完整读清代码关系，摸清真实影响面，避免闭门造方案。**本阶段只读不改。**

### 四个必查方向
1. **向下追踪**：从入口文件沿调用链逐层向下追到底（直到数据层或框架边界）。
2. **向上追溯继承链**：要改的子类 → 读清父类 / 基类 / 接口定义的全部约定与限制。
3. **向上追溯调用方**：谁引用它 → 谁调调用方 → 追到顶层入口（API / CLI / 定时任务 / 事件消费者）。
4. **横向找范式**：检查同目录或同类模块，确定项目现有命名、文件组织、错误处理与测试范式。

### 输出：四类文件清单（必须完整输出，无清单 = 未读完）

```markdown
### 直接改动
- `path/file_a.ext` — 角色：xx，改动原因：xx

### 间接相关（上游调用方）
- `path/file_b.ext` — 角色：xx，调用了 file_a

### 间接相关（下游依赖 / 基类 / 接口）
- `path/base_x.ext` — 角色：基类/接口，约束：xx

### 范式参考与已排除
- `path/similar.ext` — 范式参考：同层实现风格对齐对象
- `path/other.ext` — 已排除：同目录但属不同业务对象
```

### 规模分流判定（摸清根因后再定路径！）

基于上述真实摸底结果判断：
- **Hotfix 小修路径**（须**同时满足**以下 4 条）：
  1. 仅改动 1 个业务代码文件（测试文件除外）；
  2. 局部根因明确（如空指针防护、边界判断修正、配置拼写修正）；
  3. 不新增/修改对外 API 契约、数据库表结构、依赖包或分层架构；
  4. 不属于已在 `02-进行中/` 的多轮功能迭代。
  → 满足则跳过 Pass 2 建功能包，直接进入 Pass 3，收尾记入 `hotfix记录.md`。
- **标准功能包路径**：不满足以上任一条（跨文件改动、新功能、重构、架构/DB/API 变更）→ 必须进入 Pass 2。

## Pass 2：方案与定层落盘（关卡 2）

**目标**：把方案、分层与运维变更落盘定稿；**未落盘方案禁止修改任何业务代码。**

### 1. 建包或复用功能包（`full` / `lite` 模式）
- 新需求（需用户先评审再动手）：`python <skill路径>/scripts/godkey_gate.py new <功能名> --state draft --project-root <项目根>`
- 需求明确直接进入施工：`python <skill路径>/scripts/godkey_gate.py new <功能名> --state active --project-root <项目根>`
- 已有 `02-进行中/` 功能包的续作：直接更新原功能包的 `01-方案.md` 与 `02-进展.md`。
- `external` 模式：在对话中输出完整方案与分层改动清单，确认后再改代码。

### 2. 分层决策与跨层污染检查

对照静态架构文档确认每行新代码的归属：

```text
这段代码做什么？
├─ 路由 / HTTP / 参数校验 / 响应封装 → 接入层
├─ 业务规则 / 流程编排 / 事务边界     → 业务层
├─ SQL / ORM / 存储读写 / 队列客户端  → 数据/基础层
├─ 纯数学计算 / 统计 / 外部 API 适配  → 独立能力层
├─ 日志 / 缓存 / 鉴权等横切关注点     → 独立工具 / 中间件
└─ 说不清为什么在这一层？             → 停下来想清再写
```

| 跨层污染模式 | 典型表现 | 修正方向 |
|---|---|---|
| 数据上移 | 业务层拼接 SQL 或操控底层查询细节 | 下沉到数据层 |
| 业务下移 | 数据层夹带业务条件判断 | 上移到业务层 |
| 接口膨胀 | 接入层堆积核心编排与领域规则 | 下沉到业务层 |
| 借道访问 | 通过无关模块间接借用连接/会话 | 改为显式注入本模块依赖 |
| 跨层跳跃 | 接入层绕过业务层直调数据层 | 经由业务层编排 |
| 计算混入 | 业务/数据层堆积复杂纯计算 | 抽取至独立能力层 |

### 3. 方案落盘要求
按模板填写功能包内 `01-方案.md`（背景目标、蓝图对齐、代码摸底、分层改动清单、影响分析与运维变更、测试要点），并同步在 `02-进展.md` 写明「变更前快照」。
若处于 `01-待确认/`，等用户拍板后执行 `python <skill路径>/scripts/godkey_gate.py move <功能名> active --project-root <项目根>` 再进入 Pass 3。

## Pass 3：精准施工与清废（关卡 3）

**目标**：严格按图纸施工，保持代码干净，动态资产归位。

1. **严守改动边界**：只改 Pass 2 分层改动清单内的文件；如发现必须扩大范围，先更新 `01-方案.md` 并同步用户。
2. **范式一致**：对齐 Pass 1 找到的项目已有范式。
3. **清理纪律**：废弃字段、方法、导入、兼容桥、墓碑注释直接删除，不留“以防万一”的兜底。
4. **不顺手改无关问题**：顺眼发现的历史隐患记入 `02-进展.md` 的「待办与遗留风险」，本轮不混改。
5. **动态执行资产归入 `ops/`**：
   - 本次功能需要的迁移 SQL、一次性数据清洗/回填脚本、新增环境变量与发布顺序，**统一放进功能包的 `ops/` 目录**（如 `ops/01_alter_xxx.sql`、`ops/backfill.py`、`ops/deploy-notes.md`）；
   - 严禁把临时脚本或一次性迁移 SQL 乱塞进静态 `05-数据库/` 或业务源码树。
6. **及时更新 `02-进展.md`**：记录本次迭代实际完成项、关键决策与踩坑，确保下一次新会话能无缝接力。

---

## Pass 4：自检、审查与测试（关卡 4）

**目标**：交付前用审查标准自检，并用真实链路验证。

1. **规范自检循环**：
   - 重读项目开发规范，按 [代码审查](代码审查.md) Pass 2 的 5 个维度 + Pass 3 模式扩散逐条核查本次改动；
   - 每维度给出具体结论（禁止笼统写“通过”）；
   - 发现违规 → 立即修复 → 复检，循环直至零违规（最多 3 轮，超限中断并向用户说明）；
   - 结论写入功能包 `04-审查.md`。
2. **测试验证**：
   - 按 [测试流程](测试流程.md) 执行验证（新功能/跨文件改动在 `03-测试.md` 写明测试计划与实测报告；Hotfix 至少跑通复现与回归验证）。

---

## Pass 5：静态真相同步 & 脚本门禁验收（关卡 5 — 硬门禁）

**目标**：确保静态真相文档永远与代码同步，杜绝口头打勾。

### 1. 同步静态真相快照（按本次实际改动对照更新）
- 功能/接口/业务规则有变 → 更新 `04-功能设计/`（`lite` 为 `02-架构与设计.md`）
- 分层/模块边界/依赖选型有变 → 更新 `03-系统架构/`（`lite` 为 `02-架构与设计.md`）
- 表结构有变或 `ops/` 含 DDL SQL → 更新 `05-数据库/表结构快照.md` 与 `init_tables.sql`（`lite` 为 `02-架构与设计.md`）
- 环境变量/部署方式有变 → 更新 `07-部署运维/`（`lite` 为 `01-项目说明.md`）
- `external` 模式 → 同步原仓库对应的 `README.md` / `docs/`

> 若某项改动确不影响静态蓝图（如纯内部代码清理），须在 `02-进展.md` 独立一行写明可审计豁免：
> `<!-- doc-sync-waiver: featureDocs|archDocs|dbDocs|opsDocs | 具体原因（至少8字） -->`

### 2. 运行确定性门禁脚本并贴出结果

- **多轮迭代中（本轮结束但功能尚未全部完工）**：
  ```bash
  python <skill路径>/scripts/godkey_gate.py check-sync --package <功能包> --mode commit --project-root <项目根>
  ```
- **功能全部完成收尾（强制门禁归档）**：
  ```bash
  python <skill路径>/scripts/godkey_gate.py archive <功能包> --project-root <项目根>
  ```
- **Hotfix 收尾（核验单文件范围 + 已记台账）**：
  ```bash
  python <skill路径>/scripts/godkey_gate.py hotfix --title "..." --symptom "..." --root-cause "..." --files "..." --verify "..." --project-root <项目根>
  python <skill路径>/scripts/godkey_gate.py check-sync --mode hotfix --project-root <项目根>
  ```
- **`external` 外部项目收尾**：
  ```bash
  python <skill路径>/scripts/godkey_gate.py check-sync --project-root <项目根>
  ```
- **功能中途暂停/实验中止**：
  ```bash
  python <skill路径>/scripts/godkey_gate.py move <功能包> paused --reason "<搁置原因>" --project-root <项目根>
  ```

只有脚本输出 **`PASS`** 并向用户展示实际输出，才允许宣称本轮任务完成。

---

## 重构专项要求

1. **先理解旧设计**：明确原架构为何如此设计，盘清全部上下游依赖后才能动手。
2. **先清后建、不留过渡态**：同一重构功能包内不保留双轨兼容代码。
3. **归档同步架构文档**：重构影响模块边界或依赖方向时，必须同步静态架构文档再归档。
